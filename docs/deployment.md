# Environment deployment setup

Day 29 adds Terraform profiles and a manually triggered deployment workflow. No AWS infrastructure or GitHub environment settings were changed remotely. The full architecture diagram is planned for Day 30.

## Required inputs

In staging/prod, copy `secrets.auto.tfvars.example` to `secrets.auto.tfvars` and replace the placeholders. Supply an issued ACM certificate in `ap-northeast-1`, an existing SNS topic with confirmed subscribers and CloudWatch publish permissions, and database credentials. Configure the intended DNS hostname separately. The real input file is ignored; state and saved plans can still contain sensitive values.

Staging supports `staging_multi_az = true`; production always enables Multi-AZ. Dev preserves its instance and database defaults. Enable dev HTTPS with `enable_https = true` and an ACM ARN. CIDRs and other environment settings belong in reviewed `terraform.tfvars` files.

Each environment uses the existing state bucket with its own key. See [remote state](terraform-state.md). Staging was previously configuration-only: applying its new platform will create chargeable infrastructure.

## Restricted deployment IAM

The isolated `terraform/bootstrap/deployment-access` root requires an existing OIDC provider, exact GitHub owner/repository, and an `environments` map whose entries contain `plan_boundary_arn`, `apply_boundary_arn`, `plan_policy_json`, and `apply_policy_json`. No administrative policy is generated by default. An AWS administrator must review these policies and manage bootstrap state separately. Never bootstrap roles with the application deployment role.

Plan policies need infrastructure reads plus backend state/lock operations. Apply policies need only environment deployment actions. Restrict state keys and `.tflock` objects, bucket-list prefixes, resource scope and `iam:PassRole`; dev/staging roles must not access production resources or state. Boundaries and real policies are required inputs, not deployed guarantees. Consider separate accounts for stronger isolation.

Trust subjects are exact: `repo:OWNER/REPO:environment:ENV-plan` for planning and `repo:OWNER/REPO:environment:ENV` for apply. Plan and apply use different roles. Deployment roles are not the EC2 instance role.

## GitHub environments

Create `dev-plan`, `dev`, `staging-plan`, `staging`, `prod-plan`, and `prod`. Configure selected deployment branches/tags with exactly one branch rule named `main` for each. Protect main with pull-request review and required quality/security checks.

Plan environments can run without reviewers; dev can apply after automated checks. Staging/prod require deployment reviewers and prevent self-review. Disable administrator bypass for prod. Reviewer identities are left to the repository administrator. Built-in GitHub reviewers require one listed reviewer, not all listed reviewers; use a custom protection rule if independent multiple approvals are required.

The workflow checks these controls through the GitHub API and fails closed if settings or permissions cannot be verified. If the API cannot report the admin-bypass setting, prod remains blocked. Approval features depend on repository visibility and GitHub plan.

In every plan environment configure:

- Variables `AWS_PLAN_ROLE_ARN` and `AWS_APPLY_ROLE_ARN`, with different roles scoped to that environment.
- Secret `TERRAFORM_INPUTS`, a JSON object using only `db_username`, `db_password`, `certificate_arn`, `alarm_topic_arn`, and optionally `enable_https`.
- Secret `PLAN_ENCRYPTION_KEY`, a random passphrase at least 32 characters long.

In the matching apply environment, set `AWS_APPLY_ROLE_ARN` to the same apply role and use the same encryption key. Network/profile settings are not secret overrides. No real role/certificate/topic ARNs or credentials were invented for this setup.

## Reviewed-plan workflow

Run **Reviewed Terraform Deployment** from main and choose the environment. Apply defaults to false. Steps are automated after this controlled manual trigger; pushes do not automatically apply infrastructure.

Terraform format/validation/tests and Checkov must succeed before planning. Existing Checkov findings still block deployment. Review the redacted `terraform show` output in the plan-job logs. Sensitive credential inputs are masked by Terraform; other planned values can be logged.

The Day 29 local scan with Checkov 3.3.30 reported 220 passed checks, 76 failed checks and no parsing errors across 108 resources in the expanded environment scope. Findings were not suppressed. Syntax/validation checks, 14 mocked Terraform tests and eight deployment-control tests passed; this does not imply that security CI or live deployment is ready.

When apply is requested, environment reviewers approve the apply job after reviewing the plan. Production also requires entering `prod`. The saved plan is encrypted and retained for one day with its provider lock and environment/commit/role metadata. Apply verifies that metadata and uses the exact reviewed plan. Runs for one environment are serialized, state remains locked, and stale plans require regeneration/review.

The encryption key must match between plan and apply. Missing settings, failed scans, expired artifacts or changed state intentionally block deployment. The workflow has not been dispatched or tested against live AWS/GitHub permissions.

## Migration and recovery

Refresh dev module references with `terraform get`, then review a live plan with valid credentials. Preserve moved blocks until all relevant states have migrated. No Day 29 apply or state migration was run. See [deployment recovery](terraform-deployment-recovery.md).
